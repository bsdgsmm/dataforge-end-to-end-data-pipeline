# Data Dictionary

All data is **synthetic**: it is generated by `dataforge generate-data` and describes no real
company or person. All amounts are in USD, and all timestamps are UTC.

## Metric definitions

These definitions are implemented in `int_orders__enriched`, `fct_orders`, and
`fct_order_items`, and tested in `dbt/marketplace_analytics/tests/`.

| Term | Definition | Column |
| --- | --- | --- |
| Revenue-eligible order | An order whose status is `processing`, `shipped`, or `delivered`. `pending` orders are unpaid. `cancelled` orders never count. The rule lives in the `order_statuses` seed and is kept in sync with `contracts.py` by a unit test. | `is_revenue_eligible` |
| Gross sales | `sum(quantity * unit_price)` over an order's lines, before discounts. | `gross_sales_amount` |
| Discounts | Sum of line-level promotional discounts. | `discount_amount` |
| Net sales | Gross sales − discounts. This is what the customer is charged at checkout. | `net_sales_amount` |
| Captured amount | Sum of succeeded `charge` transactions. | `captured_amount` |
| Refunds | Sum of succeeded `refund` transactions. | `refunded_amount` |
| Net revenue | Net sales − refunds, for revenue-eligible orders. It is `0` for other orders. | `net_revenue_amount` |
| Payment balance | Captured amount − net sales. It is `0` for a correctly paid order. Non-zero values on revenue-eligible orders are reconciliation issues. | `payment_balance_amount` |
| Average order value (AOV) | Net sales ÷ number of revenue-eligible orders. | `average_order_value` |
| Repeat customer | A customer with at least two revenue-eligible orders. | `is_repeat_customer` |
| Cancellation rate | Cancelled orders ÷ all orders placed in the period. | `cancellation_rate` |
| Refund order rate | Revenue-eligible orders with any refund ÷ revenue-eligible orders. | `refund_order_rate` |
| Refund amount rate | Refunds ÷ net sales, for revenue-eligible orders. | `refund_amount_rate` |

**Attribution:** daily and monthly measures use the order date (`ordered_at` in UTC), including
refunds. A refund issued in February for a January order reduces January's net revenue. This
order-cohort view keeps each order's numbers consistent. A finance ledger would book the refund
on its own date instead; `fct_orders.last_refunded_at` supports that view.

**Shipping and taxes** are not modelled; the fictional marketplace offers free shipping and
prices include tax.

## Source files (`data/source/`)

| File | Primary key | Foreign keys | Columns |
| --- | --- | --- | --- |
| `customers.csv` | `customer_id` | – | email, first_name, last_name, country_code, city (optional), signed_up_at |
| `products.csv` | `product_id` | – | sku, product_name, category, list_price (≥ 0), is_active, created_at |
| `orders.csv` | `order_id` | customer_id → customers | order_status, ordered_at, updated_at, currency (`USD`) |
| `order_items.csv` | `order_item_id` | order_id → orders, product_id → products | line_number (≥ 1), quantity (> 0), unit_price (≥ 0), discount_amount (≥ 0) |
| `payments.csv` | `payment_id` | order_id → orders | transaction_type (`charge`/`refund`), payment_method, payment_status (`pending`/`succeeded`/`failed`), amount (> 0), created_at |

Timestamps must be ISO 8601 with an explicit offset, for example `2025-03-01T10:00:00Z`. Amounts
use at most two decimal places. `src/dataforge/contracts.py` is the single definition used by the
generator, the validator, and the raw table DDL.

## Schemas

| Schema | Owner | Contents |
| --- | --- | --- |
| `raw` | Python loader | One table per source entity, with text columns and batch metadata. |
| `audit` | Python pipeline | Run, stage, load, and data quality bookkeeping. |
| `reference` | dbt seed | `order_statuses`. |
| `staging` | dbt (views) | `stg_marketplace__<entity>`. |
| `intermediate` | dbt (views) | Reusable joins and aggregations. |
| `marts` | dbt (tables) | Dimensions, facts, and analytical marts. |

### Raw metadata columns (every `raw.*` table)

| Column | Type | Description |
| --- | --- | --- |
| `_batch_id` | text, FK → `audit.pipeline_runs` | Pipeline run that loaded the row. Part of the primary key. |
| `_source_line` | integer | Line number in the source file (header = 1). Part of the primary key. |
| `_source_file` | text | File name the row came from. |
| `_record_hash` | text | SHA-256 of the row's source values. Useful for change detection. |
| `_is_rejected` | boolean | `true` when validation quarantined the row. |
| `_rejection_reasons` | text[] | Machine-readable reasons, e.g. `invalid_type:unit_price`, `orphaned_foreign_key:order_id`. |
| `_loaded_at` | timestamptz | Load time. Staging uses it to pick the latest version. |

Indexes: the primary key on (`_batch_id`, `_source_line`), and a btree index on each entity's
business key for record lookups.

### Audit tables

| Table | Grain | Key columns |
| --- | --- | --- |
| `audit.pipeline_runs` | One row per run | `run_id`, `status` (`running`/`succeeded`/`failed`), `current_stage`, `started_at`, `finished_at`, `error_message` |
| `audit.pipeline_stage_runs` | One row per run and stage | `stage`, `status`, `attempt` (retries increment it), `error_message` |
| `audit.raw_load_stats` | One row per run and entity | `rows_received`, `rows_valid`, `rows_rejected`, `source_file` |
| `audit.data_quality_results` | One row per check result | `stage` (`source_validation`/`dbt_test`/`post_load`), `check_name`, `entity`, `severity`, `status`, `checked_records`, `failed_records`, `message`, `sample_keys` |

## Marts

Column-level descriptions for every model are in the dbt YAML files, and appear in the
documentation that `make dbt-docs` generates.

| Model | Grain | Constraints | Purpose |
| --- | --- | --- | --- |
| `dim_customers` | customer | PK `customer_id` | Customer attributes, including customers without orders. |
| `dim_products` | product | PK `product_id`, check `list_price >= 0` | Product attributes. |
| `fct_orders` | order | PK `order_id`, FK `customer_id` → `dim_customers` | Sales, payment, refund, and net revenue measures; refund status; customer order sequence. |
| `fct_order_items` | order line | PK `order_item_id`, FKs to `fct_orders` and `dim_products`, check `quantity > 0` | Line measures plus refunds allocated by net-sales share (rounded per line). |
| `mart_daily_revenue` | calendar day (UTC) | unique `revenue_date` | Orders, customers, units, gross/net sales, discounts, refunds, net revenue, AOV. Includes days with zero orders. |
| `mart_product_performance` | product | unique `product_id` | Sales and net revenue, with overall and in-category ranks and category share. |
| `mart_customer_order_summary` | customer | unique `customer_id` | Lifetime orders, net revenue, AOV, repeat flag, segment (`no_orders`, `no_completed_orders`, `one_time`, `repeat`). |
| `mart_order_status_refunds` | order month | unique `order_month` | Status mix, cancellation rate, refund order and amount rates. |

The facts and dimensions are materialized with **enforced dbt contracts**. PostgreSQL itself
rejects a duplicate key, a dangling foreign key, or a negative quantity when dbt builds the
table, in addition to the dbt tests that run afterwards.
